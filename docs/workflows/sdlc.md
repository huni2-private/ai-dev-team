# SDLC Workflow 정의

## 단계별 담당 페르소나 & 산출물

| 단계 | 담당 | 입력 | 산출물 | 완료 조건 |
|------|------|------|--------|-----------|
| Plan | PM | 요구사항 | PRD, 사용자 스토리 | 범위/우선순위 합의 |
| Design | TechLead | PRD | 아키텍처 문서, ERD, API 설계 | Dev 이해 확인 |
| Implement | Dev | Design 문서 | 동작하는 코드 | 설계 100% 반영 |
| Verify | QA | PRD + 코드 | 테스트 결과, 버그 리포트 | 합격 기준 통과 |
| Deploy | DevOps | QA 승인 | 배포된 서비스 | 운영 환경 정상 |
| Maintain | 전체 | 모니터링 | 개선 사항 목록 | - |

## 핸드오프 체크리스트

### Plan → Design
- [ ] 기능 범위가 명확히 정의됨
- [ ] 우선순위가 결정됨
- [ ] 비기능 요구사항(성능, 보안) 포함

### Design → Implement
- [ ] 아키텍처 다이어그램 완성
- [ ] API 인터페이스 정의 완성
- [ ] DB 스키마 확정
- [ ] Dev가 설계를 이해했음을 확인

### Implement → Verify
- [ ] 모든 기능 구현 완료
- [ ] 자체 테스트 통과
- [ ] 코드 리뷰 완료

### Verify → Deploy
- [ ] 모든 테스트 통과
- [ ] 버그 없음 (또는 known issues 문서화)
- [ ] 롤백 계획 수립

## 방향 이탈 감지 트리거

다음 상황 발생 시 즉시 중단하고 해당 페르소나에게 확인:

1. 설계 문서에 없는 기능 구현 시도 → TechLead
2. 요구사항 범위 밖 작업 시도 → PM
3. 기술 스택 변경 필요 → TechLead
4. 테스트 없이 배포 시도 → QA
5. QA 미통과 상태에서 배포 시도 → QA + DevOps
